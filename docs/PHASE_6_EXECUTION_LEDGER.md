bounded evidence. It does not expand Phase 5 claims or authorize future work.

### P6.2 retention blocker update

- A release-aware, five-cycle rerun reusing one generic lifecycle retained
  post-GC host RSS of 451,833,856, 530,649,088, 602,771,456, 668,454,912, and
  738,779,136 bytes after otherwise identity-stable V=512/T=8 corridor cycles.
  The sealed behavioral materialization itself retains only 1,584 host-array
  bytes from 2,414 public source-resource bytes, so this is not evidence for a
  behavior-source materialization repair.
- This is a measured P6.2 blocker, not a license for speculative cleanup. A
  generic execution-retention change would exceed the authorized config-threading
  repair and cannot be classified Class B before P6.5 freezes an external
  minimum envelope. P6.2 is therefore stopped for human direction; no P6.2
  commit or verification audit is claimed.

### P6.2 extended retention characterization — accepted closure

- The same accepted V=512/T=8, B=1 corridor and exemplar cycles were repeated
  20 times each. The harness records pre-cycle, phase, peak-current, and
  post-release/post-GC RSS, runtime compilation fields, and prepared/runtime
  identities in [P6_2_RETENTION_CORRIDOR.json](P6_2_RETENTION_CORRIDOR.json),
  [P6_2_RETENTION_EXEMPLAR.json](P6_2_RETENTION_EXEMPLAR.json), and the
  execution-only diagnostic [P6_2_RETENTION_EXECUTION_ONLY.json](P6_2_RETENTION_EXECUTION_ONLY.json).
- The accepted eager runtime remained `compiled=false` with zero compilation
  seconds, while callable, prepared-execution, architecture, layout, source,
  split, and checkpoint identities stayed stable. Corridor post-GC RSS rose to
  1,230,221,312 bytes by cycle 20. Exemplar RSS reached a 1,304,309,760-byte
  high-water mark before allocator-pressure decline and did not return to
  baseline. Disabling checkpoint/restore still reached 1,059,016,704 bytes in
  ten cycles.
- Fresh-process phase decomposition in
  [P6_2_ISOLATED_PHASES.json](P6_2_ISOLATED_PHASES.json) shows bounded
  admission/materialization and assembly, a material execution-phase increase,
  and only a transient checkpoint/restore increment. The demonstrated owner is
  therefore downstream of generic execution, consistent with JAX runtime or
  allocator retention, but no Student-owned retaining object or production
  owner is identified. The evidence does not prove a Python-object leak and
  does not prove JAX/XLA allocator behavior is harmless. No Student source-unit
  or checkpoint repair is implied.
- The Mac CPU result is a resource-envelope limitation, not a correctness
  failure. P6.2 closes with `execution_retention_observed`, `owner_unresolved`,
  and `scale_impact_pending_external_envelope`. No memory-management production
  code, cache flush, allocator control, or lifecycle teardown is added.
- P6.5 must revisit this finding on the pinned Linux/T4 environment using fresh
  repeated-cycle processes, separate host RSS and accelerator allocation/peak,
  eager/JIT comparison where supported, and official JAX allocator diagnostics
  only as diagnostic experiments. It becomes Class B only if the minimum P6.6
  envelope is prevented, and Class A only if a Student-owned retaining mechanism
  is demonstrated. P6.2 is not reopened solely because RSS does not return to
  the initial process baseline.
